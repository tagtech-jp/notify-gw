# Phase 6 並走検証チェックリスト（2026-09-22 火 〜 2026-09-28 月・7日間）

**目的**: 証跡層と通知の仕組みが「動いていること」ではなく、**人が実際にそれを使って異常に気づけること**を確かめる。

仕組みの緑だけを見ても Phase 6 は終われない。2026-09-15〜18 の Deploy 失敗は
**#alerts にも日報にも出ていたのに3日間誰も気づかなかった**（RUNBOOK §7-3）。
仕組みは全部緑だった。だからこの検証では「人が見たか」を明示的な検証項目に含める。

## 進め方

- 毎朝 **JST 09:05 の日報**が届いたら、その日の行を埋める（社長・Claude Code 双方が確認する）
- 記入した表は **Vault の日次サマリ（`inbox/notify-YYYY-MM-DD.md`）に添える**
- **欄を埋められなかった日も「未記入」として残す**。空欄は「異常なし」ではなく「見ていない」の記録であり、それ自体が検証結果になる
- 判定は最終日（09-28）ではなく**毎日**行う。3日連続で落ちた項目は、7日を待たずにその場で対処を設計する

## 検証項目

### A. 人が日報の CRITICAL 欄を見ているか（最重要）

| 見かた | 落ちたときの意味 |
|---|---|
| 日報に出た CRITICAL が、**翌営業日までに**対処または Notion 起票されているか | 見ていない。**通知を増やすのではなく、持ち越しのように「見なくても効く」形へ作り替える** |

「見た」の証拠は記憶ではなく**痕跡**で判定する（起票・修正コミット・この表への記入のいずれか）。

### B. 未解消 CRITICAL の持ち越しが機能するか

| 見かた | 落ちたときの意味 |
|---|---|
| CRITICAL が出た翌日以降、`success` が記録されるまで**毎日先頭に出続ける**か | 解消判定の SQL か配線の不具合 |
| `success` が記録された**翌日の日報から消える**か | 同上（消えないなら `agent_id`+`action` の突合が効いていない） |
| 0件の日は**欄そのものが出ない**か | 0件でも欄が出るなら、平常時に行を1つ無駄にしている |

**2026-09-21 に一度実証済み**（e-708/e-713 → e-714 success で人の操作なしに欄が消えた。RUNBOOK §7-3）。
この検証では「1回たまたま動いた」ではなく**7日間再現する**ことを見る。

### C. #alerts と日報の内容が一致するか

| 見かた | 落ちたときの意味 |
|---|---|
| 同じ事象が**両方に**出ているか | どちらかの経路が欠けている |
| #alerts の本文だけで**次に何をすればよいか分かる**か（何が起きたか / 対象 / 証跡ID / 確認先 / 対応） | テンプレートが事象に合っていない。`error_kind` ごとの文面を足す |

### D. 日報が 2000 字で切れても、重要な項目が消えないか

| 見かた | 落ちたときの意味 |
|---|---|
| 失敗・CRITICAL・WARN・死活異常が「他N件」だけに畳まれていないか | 圧縮の優先順位が壊れている（2026-09-20 に修正済みの回帰） |

### E. cto-tech-monitor（JST 06:00）が毎日証跡に入るか

| 見かた | 落ちたときの意味 |
|---|---|
| 疎通3件（Notion 収支台帳 / 台帳の隔離 / GitHub）が毎日 OK か | 接続先が変わった。**特に「売上明細が読めてしまう」は CRITICAL**（購入者ハンドル名への到達経路ができる） |
| モデル監視4件が毎日「判定できている」か（OK / deprecated / missing のいずれか） | 鍵が切れた・空になった。`missing_credential` が出たら RUNBOOK §4 の投入手順へ |

### F. デプロイ経路が CI に一本化されているか

| 見かた | 落ちたときの意味 |
|---|---|
| 期間中の本番デプロイが**すべて Actions 由来**か（`wrangler deployments list` の Author と Actions の実行履歴が一致するか） | 手元デプロイが残っている。巻き戻しの再発リスク |
| `bindings/audit` が毎日 `drifts: []` か | 申告途絶。デプロイで配線が消えた可能性 |

## 7日後の判定

| 結果 | 意味 | 次にすること |
|---|---|---|
| A が5日以上 ✅ | 日報が運用に乗った | Phase 6 の該当項目を完了とする |
| A が落ちる日がある | **仕組みではなく運用が落ちている** | 通知を増やさない。「見なくても効く」形（持ち越し・自動起票・ブロック）へ作り替える設計を1つ出す |
| B〜F のいずれかが落ちる | 仕組みの不具合 | その場で Notion 起票し、原因を特定してから次へ進む |

**この検証自体が「人が見る」ことに依存している**点は自覚しておく。表が埋まらないなら、
それは検証の失敗ではなく**A が落ちた証拠**として扱う。
